WMS Mobile App
Warehouse Management on Flutter

Designing and shipping a cross-platform mobile app that brings real-time inventory, receiving, and pick/pack operations to the warehouse floor — built end-to-end in Flutter with a Laravel REST backend.

tl;dr

What it is

A Flutter mobile app that replaces paper-based and laptop-bound warehouse operations with a single device a forwarder/picker can carry on the floor — scanning, receiving, picking, packing, and stock-checks, all syncing live to the central WMS over a Laravel REST API.

Built in-house, pair-programmed with Claude AI to accelerate UI scaffolding and targeted refactors. Currently in active rollout to the operations team timeline details on request.

problem

The bottleneck

Before the mobile app, AAI's warehouse workflows lived on a mix of desktop browser sessions, printed picklists, and manual XLSX exports. That created several friction points:

  • Pickers had to walk back and forth between the floor and a fixed workstation to confirm each step.
  • Stock counts drifted through the day because updates lagged behind physical movement.
  • Receiving inbound shipments required cross-referencing paper documents against the SAP-bridged WMS records.
  • The existing web UI wasn't built for one-handed, on-the-go use on a phone or rugged scanner-device.

The asks from operations: scan + confirm in <3 seconds, work even with shaky warehouse Wi-Fi, and keep parity with the existing web WMS as the source of truth.

approach

How I broke it down

  • Flutter for a single codebase — Android-first for the rugged warehouse devices, with iOS parity available for ops managers.
  • Laravel REST API mirroring the existing WMS endpoints — no separate "mobile backend." One source of truth, one set of business rules.
  • Offline-first reads — cached lookups for SKUs, locations, and recent transactions so a temporary Wi-Fi drop doesn't stop a pick.
  • Write-through with retry queues — every scan/confirm is queued locally and replayed on reconnect, so the database always converges.
  • AI-assisted velocity — used Claude AI to scaffold widget trees, generate test fixtures, and run targeted refactors. Human review and engineering judgment stayed in the loop for every commit.
solution

What I built

Core flows shipped:

  • Receiving — scan inbound shipments against SAP-bridged documents, with line-item validation and discrepancy capture.
  • Pick & Pack — one-handed scan-confirm flow with batch support; designed for fast repetition on the warehouse floor.
  • Stock Check & Transfer — on-floor inventory counts and bin-to-bin movements with audit trails.
  • SKU lookup — cached search across products, locations, and recent transactions for offline use.

Offline queue (Flutter side) — every action is recorded locally and replayed automatically when connectivity returns:

~/lib/sync/queue.dart 
// Hive-backed retry queue, replays in FIFO order
class SyncQueue {
  final Box<QueuedOp> _box;

  Future<void> enqueue(QueuedOp op) async {
    await _box.add(op);
    if (await Connectivity().checkConnectivity() != ConnectivityResult.none) {
      await drain();
    }
  }

  Future<void> drain() async { /* … */ }
}

lessons

What I'd do again — and differently

Worked well:

  • Treating the existing WMS REST API as the source of truth and resisting the urge to invent a "mobile API." Less divergence, simpler ops.
  • Offline-first writes with a replay queue — the warehouse Wi-Fi will drop; the question is just how gracefully you handle it.
  • AI-assisted refactors saved meaningful hours, especially when iterating UI states and adapting to operator feedback.

Would tighten:

  • Lock in an automated-test suite earlier in the rollout — especially around the offline queue replay, where edge cases are easy to miss until production traffic finds them.
  • Smaller-cohort rollouts: introduce screens to one zone or shift first, gather feedback, then expand — instead of pushing a multi-flow update broadly at once.
