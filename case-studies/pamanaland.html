Pamanaland RMS
Realty Management on Vue + Laravel

A full-stack platform for managing property inventory, agent assignments, and commission tracking — replacing the brokerage's spreadsheet-driven workflow with a clean web app the team actually wants to use.

role Full-Stack Developer

tl;dr

What it is

A web portal where Pamanaland's team manages property listings, agent assignments, and commission records in one place — with role-aware access for admins, managers, and agents, and reports they can export when month-end rolls around.

problem

The bottleneck

Before the RMS, day-to-day operations ran on a tangle of:

  • Shared Excel files for inventory — with stale rows nobody owned.
  • Email threads for assigning leads to agents.
  • Month-end commission calculations done by hand.
  • No single dashboard for management to see live pipeline state.

The team needed one source of truth they trusted, role-based access so agents only saw what was theirs, and reports they could pull without bothering IT.

approach

How I broke it down

  • Domain modelling first. Talked through real workflows with the team before writing schema — properties, units, agents, assignments, commissions, payouts.
  • Vue + Laravel monolith. Single deployment, single team, single repo. No microservices theater for a brokerage-sized product.
  • Role-aware UI. One Vue app, gated views per role. No "admin portal" / "agent portal" duplication.
  • Reports as a first-class feature. Filterable, paginated tables with CSV / PDF export rather than ad-hoc Excel dumps.
solution

What I built

Modules shipped:

  • Property & Unit management — inventory CRUD, status, pricing, ownership history.
  • Agent management — profiles, assignments, performance view.
  • Commission tracking — auto-calculated from agreement type and unit value, exportable per agent and per period.
  • Role-based dashboards — admin sees the brokerage state; agents see their own pipeline; managers see their team.
  • Reports & exports — filterable, paginated tables with CSV and PDF output for month-end review.
Live screens at portal.pamanaland.com portal is access-gated — sanitized walkthrough available on request

Example: commission calculation — one of the harder pieces since rules vary by agreement type:

~/app/Services/CommissionService.php 
class CommissionService
{
    public function compute(Sale $sale): Collection
    {
        return $sale->agreement->rules
            ->map(fn (Rule $r) => [
                'payee_id' => $r->agent_id,
                'amount'   => round($sale->price * $r->percent / 100, 2),
                'tier'     => $r->tier,
                'period'   => $sale->closed_at->format('Y-m'),
            ]);
    }
}

lessons

What I'd do again — and differently

  • Talk to the actual users first. The commission rules were more nuanced than the brief suggested — only field interviews surfaced the edge cases.
  • Ag-Grid was worth it. Sortable, filterable, exportable tables out of the box meant I didn't reinvent that for every screen.
  • Invest in seed data and a staging environment earlier — the team caught edge cases faster when they could try flows on realistic data without fear.
  • Bake more “sanity-check” queries into the admin dashboard from day one — cheap to add upfront, expensive to retrofit once reports are live.
